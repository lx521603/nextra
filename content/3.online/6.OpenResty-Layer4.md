## 背景

小鸡的 vps 可能是当地的运营商干扰，或者是其它原因，研究了一段时间，发现 443 端口的速度相当可以。非443端口在很多时候已经是直接不可用的状态，所以研究得出结论：
   1.443端口，在任何时候，都是可用的，速度还不错。
   2.443端口，在任何时候，在 YouTube 的连接速度，都是非 443 端口正常状态的时候的 2-3 倍速度。（100K vs 2-50K)

平时是用 1panel 搭建各种 web 服务，所以有了大家都跑在 443 端口的想法

## 尝试

### xhttp
xhttp 很简单，nginx 直接反代xhttp 的端口就可以,Cloudflare Worker 建立一个脚本，改写订阅链接，把反代的那个端口改写成 443 端口就可以，然后订阅链接填 Cloudflare Worker 的地址，设置一个token防止别人使用。（3x-ui没有客户端和多域名配置，也或许是我没找到）

注：xhttp 不需要 Layer 4
### Anytls
Anytls 就要用到 Layer 4 


在/opt/1panel/www/stream.d/proxy.conf文件填入
```code
# 提取 SNI 域名进行多路分流

map $ssl_preread_server_name $backend_pool {

# 1. 你的博客及所有 1Panel 网站域名 -> 丢给内部网页服务

a.com web_cluster;

# 以后如果有其他普通网站域名，也可以直接加在这里

  

# 2. 节点 A：AnyTLS 流量（匹配其特定的伪装/连接域名）

b.com anytls_backend;
 

# 3. 节点 B：Reality 流量（匹配其配置的 SNI，比如微软或苹果的合法域名）

osxapps.itunes.apple.com reality_backend;


# 4. 默认兜底：其余所有未知或普通网页流量，统一丢给网站集群

default web_cluster;

} 

server {

listen 443 reuseport;

listen [::]:443 reuseport;

proxy_pass $backend_pool;

ssl_preread on;

} 

# --- 内部后端池定义 ---

# 网页服务集群（1Panel 统一监听 8443）

upstream web_cluster {

server 127.0.0.1:8443;

} 

# AnyTLS 节点本地端口

upstream anytls_backend {

server 127.0.0.1:xxxxx;

} 

# Reality 节点本地端口

upstream reality_backend {

server 127.0.0.1:xxxxx;
}

```

把所有的 web 网站端口改到 8443，包括 openresty 自己的，在这里
```code
/opt/1panel/apps/openresty/openresty/conf/default/00.default.conf
```
记得最后重建 openresty

anytls 如果是 s-ui 搭建的话，有个比较好的功能，在节点里面，客户端那里，设置多域名，端口设置 443 这样就不用像 xhttp 还要想办法改订阅的端口。

### reality
如果上述配置好，anytls 也通了，reality 只需要把上面文件的端口号设置为实际端口号，客户端用 443 就可以。如果是订阅链接，s-ui 比较简单，多域名解决，3x-ui 用 Cloudflare Worker解决。

阅读文章，得到启发，借助大模型，添加了 tuic

```code
# --- TCP 443 统一入口 ---
server {
    listen 443 reuseport;
    listen [::]:443 reuseport;   
    proxy_pass     $backend_pool;
    ssl_preread    on;
}


# --- UDP 443 统一入口（TUIC） ---
server {
    listen 443 udp reuseport;
    listen [::]:443 udp reuseport;     
    
    proxy_pass    tuic_backend;  
    proxy_timeout 20s;
}
```
以及
```code
# TUIC 节点本地端口
upstream tuic_backend {
    server 127.0.0.1:xxxx;
}
```

遗憾： 大模型说 udp 只能选 1 个

引用大模型原话：

### 行业内如果要实现“UDP 多协议共存”，是怎么做的？

如果你在实际需求中，真的极其渴望让 TUIC 和 Hysteria 2 同时共用同一个外部的 UDP 443 端口，在工业级架构里通常不会用 Nginx，而是采用以下方案：

#### 1. 交由全功能内核接管（如 sing-box / Xray 统一入站）

不让 Nginx 管 UDP 443，而是把系统的 UDP 443 直接交给一个支持多协议复用的高性能网关内核（例如 sing-box）。

sing-box 在底层通过特殊的协议多路复用技术，在一个端口里同时监听并解包多种现代协议。

#### 2. 多端口独立直通（最稳妥的妥协）

正如我们前面所见，TCP 走 443 端口复用（吃满网页和各种代理的 SNI 分流），而 UDP 则给主力协议（如 TUIC）独占 443，如果非要用第二个 UDP 协议，就让他走一个高位独立端口。
